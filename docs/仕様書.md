# Play 更新履歴アーカイブ 仕様書

版: 0.2
日付: 2026-09-28
状態: 実装前の合意用

## 1. 背景

Google Play のアプリ詳細に出る「新機能」（What's new）は、その時点の最新リリース分だけである。開発者が次の版を出すと、前の文面はストア上から消える。

そのため、前回見たときが 1.0 で、次に開いたときが 1.4 だと、1.1〜1.3 の更新内容はストア上に残っていない。アプリの利用者が更新理由を追いたいとき、および開発者が他アプリのリリース間隔を観察したいときに、この上書きが問題になる。

公式の「過去のリリースノート一覧」API は一般公開されていない。公開ページを定期的に読み、その瞬間に載っている版と文面をこちらで保存する以外に、無料で確実な手段はない。

## 2. 目的

監視対象アプリについて、公開ページに出ている版・更新日時・新機能文面を定期取得し、変化したときだけ履歴として残す。後から「いつ、どの版で、どんな文面だったか」をローカルに追えるようにする。

成功の定義は次のとおり。

- 監視間隔のあいだに公開されていたリリースは、版と新機能文面が履歴に1件残る。
- 同じ内容の再実行では履歴が重複しない。
- 版番号が飛んだときは、「間の版はストアから消えており、このツールでは復元できない」ことが履歴上で分かる。
- 取得失敗で、それまで溜めた履歴が壊れない。

## 3. このツールが解決できることと、できないこと

### 解決できること

監視を始めたあと、次の取得までにストアへ載っていた最新の文面を保存できる。間隔を短くするほど、連続リリースの取りこぼしは減る。

例: 月曜に 1.0、火曜に 1.2、木曜に 1.4 が出て、毎日1回取得できた場合、履歴には 1.0 / 1.2 / 1.4 の3件が残る。

### 解決できないこと

次は仕様上の制約であり、不具合ではない。

- **取得と取得のあいだに出して消えた版は復元できない。** 1.0 の次の取得時点でストアがすでに 1.4 なら、1.1〜1.3 の文面は公開ページに存在しない。ツールは「1.0 から 1.4 へ飛んだ」と記録し、欠番の疑いを付けるところまでが限界である。
- **監視開始より前の履歴は集まらない。** 初回実行は、そのときの最新1件を基点として保存するだけである。
- **端末ごとの段階的ロールアウトの全変種は分からない。** ウェブのアプリ詳細は、言語・国を指定したときの代表値を返す。`version` が `Varies with device` になるアプリがある。
- **開発者が書かなかった更新内容は生まれない。** 新機能欄が空、または前回と同じ文面のまま版だけ進むことがある。
- **ストアの HTML 構造変更で取得が止まることがある。** 使用ライブラリは非公式で、Play の内部データ配置が変わるとフィールドが欠ける。

有料のマーケットデータ API（過去数日〜数年の changelog を返すサービス）を使えば、取りこぼし後の復元は可能になる。本仕様の対象外とし、将来の任意拡張としてのみ言及する。

## 4. スコープ

### 4.1 今回作るもの（MVP）

- パッケージ名の監視リスト
- 日本語・日本ストア（`lang=ja`, `country=jp`）でのアプリ詳細取得
- 変化があったときだけ追記するローカル履歴（JSON）
- 版飛び（欠番の疑い）の記録
- 履歴 JSON の最新値を Google スプレッドシートへ書く。1アプリ3列（アプデ日、Ver.、内容）。対象シートは `自動取得`。既存の週次表（シート1）は上書きしない。

### 4.2 今回作らないもの

- GUI、Web 画面
- レビュー本文の収集
- インストール数や評価の時系列（取得はしてもよいが、履歴の主題にしない）
- 過去に消えたリリースノートの復元
- 端末に入っているアプリ一覧との自動同期
- ログインが必要な情報、非公開トラック（内部テスト等）の取得

### 4.3 次段階（MVP のあと）

- 定期実行（GitHub Actions で毎日 09:00 JST。履歴 JSON をリポジトリにコミットする）

通知と定期実行は、履歴の保存が安定してから足す。MVP の完了条件には含めない。

## 5. 利用者と操作

想定利用者は、自分が見ているアプリの更新文面を残したい個人である。同時に見るアプリ数は、当初 1〜30 件程度とする。

主な操作は次の3つ。

| 操作 | 内容 |
| --- | --- |
| 監視リスト編集 | パッケージ名を追加・削除する |
| 巡回 | リスト全件を取得し、変化があれば履歴へ追記する |
| 閲覧 | あるアプリの保存済み履歴を、新しい順に見る |

パッケージ名は Play の URL の `id=` である。例: `https://play.google.com/store/apps/details?id=com.twitter.android` の `com.twitter.android`。

## 6. 機能要件

### 6.1 監視リスト

- 設定ファイルにパッケージ名を列挙する。1行1件、または YAML / JSON の配列。
- 空行と `#` 始まりのコメント行は無視する。
- 重複したパッケージ名は1件として扱う。
- パッケージ名の形式は `^[a-zA-Z][a-zA-Z0-9_-]*(\.[a-zA-Z][a-zA-Z0-9_-]*)+$` に合わないものを巡回前に拒否し、理由を表示する。
- App Store のアプリは `ios <バンドルID>` または `ios <数字のトラックID>` と書く。履歴のキーは取得できたバンドルIDとする。
- リストに無いアプリの履歴は消さない。リストから外したあとも、過去分は閲覧できる。

### 6.2 取得項目

1アプリにつき、次を取得する。ライブラリが返す名前は実装時に固定し、仕様上の名前は右列とする。

| 仕様上の名前 | ライブラリのフィールド（Python `google-play-scraper`） | 必須 |
| --- | --- | --- |
| パッケージ名 | 引数の app id | はい |
| アプリ名 | `title` | はい |
| 版 | `version` | はい（空なら空のまま保存） |
| ストア上の更新時刻 | `updated`（UNIX 秒） | はい |
| 新機能文面 | `recentChanges` | いいえ（無いアプリは空文字） |
| 詳細ページ URL | `url` | いいえ |
| 開発者名 | `developer` | いいえ |

新機能文面は、Python 版 `google-play-scraper` 1.2.7 では抽出が無効になっている。実装は同じ公開ページを 1 回だけ取得し、`title`・`version`・`updated`・`developer`・`url` はライブラリの項目定義から読む。新機能文面はページ内データ `ds:5` の `[1, 2, 144, 1, 1]` から読む。配列の末尾がオブジェクトになっている版では、キー `"145"` を代わりに見る。どちらも無い、または空なら空文字とし、取得全体は失敗にしない。`version` が取れないときは、ライブラリと同じく `Varies with device` として保存する。

取得時の言語・国は既定で `ja` / `jp`。設定で上書きできる。同じアプリを複数の言語で二重管理することは MVP ではしない。

### 6.3 変化の判定

各アプリについて、直近に保存したスナップショットと、今回の取得結果を比べる。比較キーは次の組である。

1. 版文字列 `version`
2. ストア更新時刻 `updated`
3. 新機能文面を正規化したあとのハッシュ

文面の正規化は、前後の空白を除き、改行コードを `\n` にそろえる。HTML タグが混じる場合はタグを除いてから比較する。

判定は次のとおり。

| 状態 | 動作 |
| --- | --- |
| 履歴がまだ無い | 初回スナップショットとして1件保存する。通知用の「新バージョン」には数えない |
| 3つとも一致 | 何も追記しない。最終確認時刻だけ更新してよい |
| いずれかが違う | 履歴に1件追記し、直近スナップショットを置き換える |

版文字列だけを見ない。次のケースを取りこぼす、または誤検知するためである。

- 版が `Varies with device` のまま、更新時刻や文面だけ変わる。
- 同じ版番号のまま、開発者が新機能文面を書き換える。
- 版は進んだが、文面が空、または前回のコピペのままである。

### 6.4 欠番の疑い

版が同じときの文面変更や更新時刻の変化では、`gapSuspected = false` とする。版が違うときだけ、次の規則で判定する。

版文字列は、数値を `.` または空白で区切った列（例: `1.2.3`, `1.4`, `2026.09.1`）として読む。どちらかが読めない場合（`Varies with device`、空、`1.2-beta` など）は `gapSuspected = false`、`versionCompare = "unparsed"` とする。欠番は推測で立てない。

両方読めたときは、短い方の末尾を 0 で補ってから左から比べる。

- 補った列が同じ（`1.2` と `1.2.0`）なら、欠番の疑いなし。
- 最初に違う桁がちょうど +1 で、それより下の桁がすべて 0 なら、欠番の疑いなし。最下位だけの +1（`1.0.0` → `1.0.1`、`1.9` → `1.10`）と、繰り上がり（`1.9` → `2.0`、`1.2.3` → `1.3.0`）がここになる。末尾が増えて 0 または 1 になる場合（`1.2` → `1.2.0`、`1.2` → `1.2.1`）も、0 補完したあとこの規則に合う。
- それ以外は `gapSuspected = true`、`versionCompare = "parsed"` とする。`1.0` → `1.4`、`1.2.3` → `1.4.0`、`1.2` → `1.2.2` がここになる。

`gapSuspected` の意味は「番号が飛んで見える。飛んだあいだの文面は、この取得では入手していない」である。ストアが版を飛ばしてリリースした（1.3 を出さずに 1.4 にした）場合も同じフラグになる。両者は公開情報だけでは区別できない。履歴の表示では、その旨を一文で示す。

### 6.5 履歴の不変条件

- 追記のみ。過去エントリの文面・版・取得時刻は書き換えない。
- 同一アプリで `(version, updated, changelogHash)` が既存の最新エントリと一致する追記はしない。
- 途中のエントリが同じ組を持つ場合（版が戻った、同じ文面が再掲された）は、新しい取得として追記してよい。上書きはしない。
- 保存は、一時ファイルへ書いてから置き換える。書き込み中の失敗で履歴ファイルが空にならないようにする。
- アプリ 1 件の処理が終わるたびに履歴ファイルへ書く。巡回の途中で止まっても、終わった分は残る。

### 6.6 失敗時

アプリ単位で失敗を隔離する。1件が落ちても、残りのアプリの巡回は続ける。

| 失敗 | 扱い |
| --- | --- |
| アプリがストアに無い、非公開、地域制限 | そのアプリを失敗として記録し、既存履歴は維持する |
| 通信エラー、タイムアウト | 同上。その回のスナップショットは更新しない |
| 必須フィールド `title` が取れない | ライブラリ破損の可能性として失敗にする。部分的な空レコードは保存しない |
| `version` または `recentChanges` が欠けている | 取得成功。欠けた項目は空として比較する |
| 履歴ファイルの JSON が壊れている | 巡回を開始しない。退避ファイル名を表示して停止する |

終了コードは、全件成功が 0、一部失敗が 1、設定または履歴ファイルが読めず1件も処理できない場合が 2。

### 6.7 閲覧

- 引数なしの一覧は、監視中アプリの名前、最新版、最終確認時刻、履歴件数を出す。
- パッケージ名を指定した詳細は、履歴を新しい順に出す。各件に、取得時刻、版、ストア更新時刻、欠番の疑い、新機能文面を含める。
- 文面が空のときは「ストアに新機能の記載なし」と表示する。

## 7. データ

履歴ファイルはリポジトリ直下の `data/history.json` を既定とする。設定でパスを変更できる。`data/` は利用者データなので、サンプル以外は git に含めない（`.gitignore`）。

```json
{
  "schemaVersion": 1,
  "apps": {
    "com.example.app": {
      "title": "例のアプリ",
      "url": "https://play.google.com/store/apps/details?id=com.example.app&hl=ja&gl=jp",
      "developer": "Example",
      "latest": {
        "version": "1.4.0",
        "updated": 1750000000,
        "recentChanges": "不具合を修正しました",
        "changelogHash": "sha256:...",
        "fetchedAt": "2026-09-28T02:00:00Z"
      },
      "lastCheckedAt": "2026-09-28T02:00:00Z",
      "lastError": null,
      "history": [
        {
          "version": "1.4.0",
          "previousVersion": "1.0.0",
          "updated": 1750000000,
          "recentChanges": "不具合を修正しました",
          "changelogHash": "sha256:...",
          "fetchedAt": "2026-09-28T02:00:00Z",
          "gapSuspected": true,
          "versionCompare": "parsed"
        }
      ]
    }
  }
}
```

- 時刻の保存形式は UTC の ISO 8601。`updated` のみストア由来の UNIX 秒を維持する。閲覧用 Markdown の日時は日本時間（JST）で出す。
- `history` は古い順の配列とする。表示時に逆順にする。
- `changelogHash` は正規化後文面の SHA-256 とする。

設定ファイル `watchlist.txt` の例:

```text
# パッケージ名を1行に1つ
com.twitter.android
jp.naver.line.android
```

任意設定 `config.toml`（無くても動作する）:

```toml
lang = "ja"
country = "jp"
history_path = "data/history.json"
watchlist_path = "watchlist.txt"
request_interval_seconds = 1.0
table_path = "README.md"
```

アプリとアプリのあいだは、既定で 1 秒空ける。連続アクセスを避けるため、0 にはしない。

## 8. コマンド

実装言語は Python 3.11 以上。依存は `google-play-scraper` のみを原則とする（標準ライブラリで JSON・ハッシュ・ファイル置換を行う）。

```text
python -m playarchive check          # 監視リストを巡回して履歴を更新
python -m playarchive list           # 保存済みアプリの概要
python -m playarchive show <pkg>     # そのアプリの履歴
python -m playarchive peek <pkg>     # ストアの現在値だけ表示し、履歴は書かない
python -m playarchive sheets         # history.json の最新値をスプレッドシートへ書く
python -m playarchive table          # history.json から README.md の表を作る
```

`check` の標準出力は、アプリごとに1行の結果とする。

```text
ok        com.example.app  1.0.0 -> 1.4.0  gap
unchanged jp.naver.line.android  15.1.0
failed    com.missing.app  not found
baseline  com.new.app  3.2.1
```

`gap` は欠番の疑いがある追記、`baseline` は初回保存である。

## 9. 実行環境

- 開発と MVP の実行は、利用者の PC 上の手動実行で足りる。
- ネットワークは、Play の公開ページ、Apple の lookup API、YYデスクトップ字幕のリリースノートページへの HTTPS が出られればよい。API キーは不要。
- 資格情報、Cookie、端末の Google アカウントは使わない。
- 次段階で GitHub Actions にする場合も、コミットしてよいのは履歴 JSON と設定だけとする。Webhook URL はリポジトリに置かず、Actions の secret にする。

推奨の巡回間隔は、MVP では利用者が決める。目安は1日1回。取りこぼしをさらに減らすなら 6〜12 時間に1回。数分間隔の常時巡回は、個人の監視リストには過剰であり、ストア側の制限を受けやすいので既定にしない。

## 10. 非機能

- 30 アプリの巡回が、各1秒間隔を含めて 2 分以内に終わること（ストアが通常応答する場合）。
- 履歴が数千件になっても、追記のたびに全件を読み書きしてよい。件数が問題になるのは、1アプリあたり数万件になってからなので、MVP では SQLite にしない。
- 実行ログの出力先は標準出力だけとする。ログファイルは作らない。`check` はアプリごとに結果を 1 行出す。新機能文面の全文はそこには出さず、履歴ファイルに残った文面を正とする。
- 取得失敗の記録は、標準出力の 1 行に加え、当該アプリの `lastError`（`at` と `message`）へ残す。成功した取得では `lastError` を `null` に戻す。
- ライブラリの更新でフィールド名が変わった場合に備え、取得結果から仕様上の項目へ写す処理を1か所に閉じる。

## 11. 受け入れ条件

次を満たしたら MVP 完了とする。

1. 実在するパッケージを `peek` すると、アプリ名・版・新機能文面（空ならその旨）が表示される。
2. 空の履歴に対する最初の `check` で、`baseline` が1件保存される。同じ状態でもう一度 `check` すると追記件数は増えない。
3. テスト用に、前回スナップショットの版だけを古い値へ変えてから `check` すると、新しい履歴が1件増え、番号が飛んでいれば `gapSuspected` が true になる。ストアへ「偽の過去版」を要求するテストは行わない。
4. 版が同じで文面だけ違うフィクスチャでは、追記される。版・更新時刻・文面がすべて同じフィクスチャでは、追記されない。
5. リストの2件目が取得失敗しても、1件目の成功分は保存され、プロセスは終了コード 1 で終わる。
6. `1.9` の次が `1.10` のとき、欠番の疑いにならない。`1.0` の次が `1.4` のときは欠番の疑いになる。

自動テストは、ネットワークを使わない。取得層は差し替え可能にし、フィクスチャの辞書で 3〜6 を検証する。項目 1 だけ、実装者の手元で実ストアに1回アクセスして確認する。

## 13. 決定事項

1. 履歴 JSON（`data/history.json`）を git で残し、GitHub Actions が毎日 09:00 JST に巡回して差分があれば `README.md` を更新してコミットする。
2. 初回の baseline は履歴配列に含める。表示上は監視開始時の記録とし、`check` の結果は `baseline` とする。`ok`（更新検知）には数えない。
3. 通知は作らない。Google スプレッドシートへの書き込みは使わない。
4. 実行ログは標準出力のみとする。
5. 履歴ファイルはアプリ 1 件ごとに保存する。
6. サービスアカウント鍵は置かない。Apps Script は使わない。
